## Task 4 — Time and geometry helpers [done]

- **`src/domain/time.ts`** (new) holds the seven responsibilities the plan lists, all pure functions of numbers, so the grid, the editors, and the progress sentences cannot disagree about what a number means. Exported: `DAY_SPAN_MINUTES` (= 960, derived from `DAY_END_MINUTE - DAY_START_MINUTE`, never re-typed), a `MinuteRange` interface (`startMinute`/`endMinute`, half-open), `formatClock`, `formatDuration`, `snapDragMinute`, `isOnTypedStep`, `isWithinDay`, `rangesOverlap`, `topPercent`, `heightPercent`. Constants are imported from `@/domain/types` rather than re-derived, so task 3's pinned numbers stay the single source. No `Date` anywhere, no `any`.
- **Clock text** is 24-hour with no leading zero on the hour and always two digits on the minutes: `8:00`, `9:30`, `17:00`, and the day edges `6:00`/`22:00`. A loop over all 1441 minutes of a day asserts the shape `^\d{1,2}:\d{2}$`, so no minute can print as `8:5` or `08:00`.
- **Duration text** drops the minutes on a whole hour and the hours before one, so a 300-minute quota reads `5 hours` and a 100-minute session reads `1 hour 40 minutes` rather than a decimal. The four documented strings are asserted verbatim, plus the 59/60 boundary, `1 minute` vs `2 minutes`, `1 hour 1 minute`, and `0 minutes` for absent travel (a length, not a silence). A loop over 0–720 asserts the text never contains `60 minutes`, which is the one wrong-looking thing a naive `Math.floor` split can produce.
- **Drag snap** is the nearest quarter hour. The tie the plan asked to be documented cannot actually happen: a 15-minute step would have to cut a whole minute in half to reach one, and 7.5 minutes past is not a time the board can hold. The test says so in a comment and then pins the real behaviour from both sides — 6:07 is 7 minutes past and 8 short, so it snaps back to `6:00`; 6:08 flips the distance and snaps forward to `6:15`. A loop over the whole day asserts every result is on the step, is idempotent, and moves no more than half a step (7.5 minutes, never reached).
- **Typed step** is five minutes: `isOnTypedStep(100)` for 1:40 is true, 1:37 is false, and 6:00/22:00 are both fine. A field that misses the step is refused by the caller, not snapped — `snapDragMinute(100)` is 105, which is exactly why the two rules stay separate (asserted in a closing test that the steps really are 15 and 5).
- **Bounds** are day edges only: `isWithinDay({360, 1320})` accepts the whole visible day (so a block may start at 6:00 and end at 22:00), `{720, 840}` accepts a block in the 12:00–14:00 hole, and 5:55 / 22:05 are refused. The function deliberately says nothing about length — the minimum-length rules belong to the mutations that return `too-short`.
- **Overlap** is `a.start < b.end && b.start < a.end`, so touching stretches are allowed (8:00–12:00 against 12:00–14:00, and a commute ending exactly at the work start) while any shared minute, including full containment, is refused. One test case caught a real mistake while writing it: I had claimed 700–800 was clear of 480–720, and the assertion failed correctly. Fixed the fixture to 14:10–15:00, which is genuinely free.
- **Geometry** is expressed as the `GridBlockView` field names the plan defines: `topPercent(minute)` puts 6:00 at 0, 12:00 at 37.5, and 22:00 at 100, and `heightPercent(minutes)` makes a 15-minute block `(15 / 960) * 100` and a 100-minute block `(100 / 960) * 100`. The 960 lives inside this module, so the offset from 6:00 cannot be forgotten at a call site the way a bare subtraction could.

## Task 5 — Preset board [done]

- **`src/domain/board.ts`** (new) is the blank week and nothing else: no commute, no goals, no sessions, no one-offs, no done marks, `version: 1`. Monday–Friday each get two work intervals, 480–720 and 840–1020 (8:00–12:00 and 14:00–17:00); Saturday and Sunday get an empty `DayPlan`. The 12:00–14:00 hole is deliberately *not* an object — the test proves it is free because no interval covers it, which is the product scope's "a hole is just time with no work interval".
- **`export type CreateId = () => string`** lives here, not in `types.ts`, because the plan's own listing for `types.ts` is already fixed and every mutation in tasks 8–15 takes one of these. Ids are never generated in this module: the app passes `crypto.randomUUID` at the edge, tests pass a counter, so nothing depends on the platform.
- **`createDefaultBoard(createId)`** spells the seven days out in a literal instead of looping over `DAYS`. A `Record<DayId, DayPlan>` built by `reduce` would have needed an `as` cast on the accumulator, and the literal buys a real check instead: a new day in the union fails the build here with TS2741 rather than turning into a day with no plan. Proved by deleting `saturday:` and running `tsc -b --force`.
- **`resetBoard(createId)` takes no board on purpose.** Reset discards the whole document — task definitions included, per the product scope — so there is nothing to carry over; the orchestrator replaces its state with the result and saves, which is also why the plan gives it the same one-argument signature as `createDefaultBoard`. It is a named entry point rather than an alias by accident: the reset flow and the first open read differently at the call site.
- **`src/domain/board.test.ts`** (new, 16 tests) builds every board through a counting id source (`id-1`, `id-2`, …), so the tests state what the board *is* rather than only that the ids are unique. It pins the preset minutes as `[480, 720]` and `[840, 1020]` for each of the five weekdays (and separately as `8:00–12:00` clock text, to prove the two modules agree), the empty weekend, `0` commute in both directions on all seven days, the empty `goals`/`sessions`/`oneOffs`, and `version: BOARD_VERSION`. The id test asserts the full `id-1`…`id-10` sequence — five weekdays at two intervals each, and nothing else needing an id yet — and that the ids on the board are exactly those, in order, with no repeats.
- **Non-mutation is tested from both directions.** One test builds two boards, then edits the first the way a work edit will (pops a work interval, sets a commute, adds weekend work, pushes a goal, a session, and a one-off) and asserts the second still deep-equals a `structuredClone` taken at birth. A second test asserts the boards hold different `DayPlan` objects, different interval objects, and different array references, then mutates a *minute* on the first board's Monday interval and reads it back off the second. Also checked: the preset's own intervals are inside 6:00–22:00, do not overlap each other, and leave 12:00–14:00 free — the rules tasks 7 and 8 will enforce, checked here so a bad preset fails early.
- **Two test bugs were caught by running them, and one guard was proven to bite.** The id helper returned the log array where its own type said `() => string[]` (Vitest transpiles without typechecking, so only `tsc` would have seen it), and the non-mutation test compared against a freshly built board whose ids had moved on — both fixed by cloning a snapshot instead. To confirm the tests really catch a shared `DayPlan`, I made Monday and Tuesday share one object: the id test failed as expected (nine ids issued, not ten), then the file was reverted.
